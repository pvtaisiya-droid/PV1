## Компоненты и границы

```text
PV1: Case → IcsrRevision → сохранённый IcsrExportArtifact
  → явная авторизованная команда → AS2Dispatch → AS2Attempt
  → отдельный app.as2_worker → аутентифицированный loopback adapter
  → движок A: SQLite spool → pyas2lib → подписанный/зашифрованный POST
  → движок B: durable inbox → проверка/расшифрование
       → подписанный асинхронный MDN на A /mdn
       → отдельный подписанный/зашифрованный локальный ACK на A /as2
  → A сохраняет входящие ответы независимо от БД PV1
       → подписанный MDN на полученный ACK на B /mdn
  → worker архивирует события/ACK → отдельные MDN/ACK-состояния PV1
```

`app/as2_engine.py` — небольшой локальный HTTP/SQLite host готовой библиотеки; он не реализует CMS, подпись, шифрование, MIME-каноникализацию или расчёт MIC. Эти операции выполняет pyas2lib. PV1 выбирает сохранённый артефакт, разрешает отправку, хранит намерение/попытки/результаты и аудит. `app/as2_adapter.py` — единственная граница PV1 → движок. Разбор прикладного ACK отделён в `app/as2_ack.py`.

Два движка запускаются независимыми процессами с разными AS2 ID, ключами и SQLite. Входящее сообщение сохраняется до HTTP 200, затем обрабатывается асинхронно. Фоновый worker не зависит от браузера или веб-процесса. Долгая сетевая операция проходит вне транзакции PV1.

Новые файлы: `app/as2_{settings,adapter,engine,ack,queue,worker}.py`, `app/routers/as2.py`, `app/templates/as2.html`, миграция `20261111_0035_as2_local_queue.py`, `tools/as2_stand.py`, `tools/as2-requirements.lock.txt`, `config/as2-contours.example.json`, `tests/test_as2_local.py`, `tests/as2_crypto_probe.py`. ## Доверие, конфигурация и идентификаторы

`PV_AS2_CONFIG` указывает на закрытый versioned registry `pv1-as2-local-1`. Генератор создаёт CA и два разных leaf-сертификата; CA private key не сохраняется. Leaf действуют 30 дней, CA — 60 дней. Перед упаковкой и каждой отправкой проверяются период действия, SHA-256 fingerprint и цепочка доверия; `validate_certs=True`, `ignore_self_signed=False`. Собственный ключ также сверяется с сертификатом. Приватные PEM зашифрованы, пароль/ключ/control token лежат только в закрытом runtime-каталоге. Windows ACL убирает наследование и даёт доступ текущему пользователю. Эти секреты не попадают в Git, UI, отчёт или обычные логи.

Control API требует секретный Bearer token с отдельным значением у каждой стороны; интерфейс PV1 не принимает от пользователя событий «подпись проверена». `PV_APP_MODE` не определяет контур. Приёмники слушают только **127.0.0.1**; URL вне loopback, перенаправления, прокси и произвольные обратные MDN-адреса запрещены. Шифрование/подпись защищают собственно AS2, внутренний API ограничен локальной машиной, token и правами ОС. Это граница управляемого стенда с доверенным владельцем ОС, не продуктивный сетевой периметр.

Примерные постоянные адреса нового стенда:

| Сторона | AS2 ID | AS2 / входящий ACK | Асинхронный MDN |
|---|---|---|---|
| A, PV1 | PV1-LOCAL-A | `http://127.0.0.1:18741/as2` | `http://127.0.0.1:18741/mdn` |
| B, получатель | PV1-LOCAL-B | `http://127.0.0.1:18742/as2` | `http://127.0.0.1:18742/mdn` |

XML Sender/Receiver: `SYNTH-SENDER` / `SYNTH-RECEIVER`. Несогласованность адресата/контура с frozen envelope, purpose не `local_test`, непрошедшая локальная проверка, отсутствующий/изменённый XML блокируют отправку. Повторной сериализации XML нет.

`config/as2-contours.example.json` содержит отдельные отключённые `rzn_test` / `rzn_prod` с пустыми параметрами. Исполняемый registry допускает только `local_stand`. Исторические сертификаты и адреса РЗН не загружаются.

Различаются Case ID, Revision ID, Artifact ID, Dispatch ID, Attempt ID, AS2 Message-ID, E2B batch/message ID и ID событий/результатов ACK. Команда пользователя имеет UUID и checksum параметров; повтор возвращает прежнее намерение. Дополнительная уникальность artifact/contour/recipient не даёт создать вторую независимую очередь того же сообщения. Техническая попытка не создаёт клиническую ревизию или XML.

Правило технических повторов основано на [RFC 4130 §§5.3.3, 5.4–5.5](https://www.rfc-editor.org/rfc/rfc4130#section-5.5): повторное использование Message-ID связано с идентичностью всего сообщения, включая Date; пределы повторов задаются соглашением сторон. Здесь повтор движка использует сохранённые MIME-байты, заголовки, Date и прежний Message-ID. Явная новая попытка после подтверждённого сбоя до доставки получает другой Attempt UUID и новый Message-ID `<UUID@pv1-local.invalid>`. Таймаут не трактуется как доказательство недоставки.

## Очередь, события, ручные действия

CAS-захват задания с lease 30 секунд защищает получение двумя worker. Результат handing-off сначала сверяется по Attempt ID с историей движка. Crash после сохранения `requesting` и до известного результата не допускает слепого нового POST. Engine перед сетью фиксирует `sending`; после рестарта такое состояние становится `unknown`, а не `pending`. Блокировка единственного владельца engine-файла берётся до восстановления. Потеря/замена engine history ID даёт неопределённость.

**Единственный владелец автоматических сетевых повторов — engine host.** Только отказ подключения до доставки допускает до 3 HTTP-вызовов с сохранёнными байтами, задержками 2/4 секунд (общая формула с пределом 10 секунд). HTTP timeout — 3 секунды. Таймаут, потерянный HTTP-ответ, неизвестный исход, отрицательные MDN/ACK не создают автоматическую новую попытку. HTTP 200 означает только сохранение входящего транспорта. Exactly-once сеть не обещается.

| Состояние PV1 | Смысл / дальнейшее действие |
|---|---|
| queued / dispatching | Намерение сохранено / передаётся движку |
| reconciling | Повторно читается долговременная история, не создаётся новый транспорт |
| not_delivered | Подтверждён сбой до доставки; уполномоченный пользователь может разрешить новую попытку с основанием |
| uncertain | Возможная доставка с неизвестным исходом; сверка и разбор, без кнопки слепого повтора |
| waiting_mdn / mdn_overdue | Ожидается проверенный MDN; локальный порог 30 секунд |
| waiting_ack / ack_overdue | MDN положителен, ACK ещё не установлен; локальный порог 60 секунд |
| mdn_negative / ack_rejected | Раздельные отрицательные транспортный/прикладной результаты |
| requires_review | Недостоверный ответ, неизвестный прикладной код, несовпадение идентификаторов либо противоречивые события |
| locally_acknowledged | Проверены положительный MDN и положительный **локальный** ACK; публикация всё равно `not_confirmed` |

Пороги отсчитываются от начала технической попытки; превышение меняет мониторинг, а не запускает пересылку. Они не заменяют срок представления случая. 72 часа из исторической инструкции РЗН не превращены в универсальный таймаут.

События engine имеют постоянные engine ID / sequence. Их повторное получение идемпотентно. Raw MIME и расшифрованный ACK записываются с SHA-256 до применения результата; архив сверяется при чтении. Engine хранит приём независимо от доступности БД PV1. Сохраняются несопоставленные ответы, повторные/поздние уведомления и результаты, пришедшие в другом порядке. ACK до MDN не выдумывает отсутствующий MDN. Разные результаты не затирают друг друга: возникает конфликт. Служебная отправка нашего MDN может отображаться в общем списке событий без привязки к исходящему ICSR — это не новая бизнес-отправка.

SQLite-миграция добавляет неизменяемость исходных сведений намерения/события и запрет удаления транспортной истории. Изменяемы производные состояния и сопоставление, а не raw evidence. Исторические отправки не создаются задним числом.

Экран `/as2` и `/cases/{case_id}/as2` показывает ревизию, артефакт, контур, попытки, Message-ID/MIC, независимые MDN/ACK, ожидание, ошибки, сертификаты и архивы. Несопоставленные оригиналы доступны уполномоченному пользователю из общего монитора. Ручные действия — сверить историю или разрешить повтор **только** после подтверждённой недоставки; нужны `view`, `export`, `icsr_workflow`, причина, актуальная версия, аудит автора; HTML защищён CSRF. Кнопки «считать успешно» нет. Подмена Case/Dispatch/Event ID отвергается. Отправка frozen artifact не изменяет и не разблокирует клиническую карточку.

## Проверка MDN и локальный ACK

MDN: движок проверяет доверенную подпись и MIC, host дополнительно требует ожидаемые AS2 From/To, Original-Message-ID/recipient, наличие совпадающего received-content-MIC и SHA-256. Положительный disposition без этих условий не даёт успеха. Сохраняются исходные заголовки/байты и metadata результата; engine сохраняет время приёма/события, PV1 — время архивирования и, для новых событий, `engine_created_at`.

ACK передаётся отдельным AS2-сообщением; после проверки подписи и расшифрования точный payload сохраняется, затем разбирается адаптером **`pv1-local-ack-1`**. Это документированный синтетический JSON-контракт, не профиль ICH ACK и не ACK РЗН:

```json
{
  "profile": "pv1-local-ack-1",
  "batch_id": "точный E2B batch ID",
  "artifact_sha256": "SHA-256 полученных XML-байтов, 64 символа",
  "original_as2_message_id": "Message-ID подтверждаемого ICSR без угловых скобок",
  "results": [
    {"message_id": "точный E2B message ID", "code": "accepted", "detail": "тестовое описание"}
  ]
}
```

Допускаются 1–100 разных результатов; коды `accepted`, `rejected`, `review`. Неизвестный профиль/структура/код требуют разбора. Локальный `accepted` означает, что синтетический получатель архивировал проверенное содержимое; не означает клиническую/регуляторную валидацию. Для текущего односообщенческого артефакта ожидается точное множество из одного E2B message ID; лишние/недостающие результаты блокируют признание успеха. Все результаты хранятся отдельно. Сопоставление: original AS2 Message-ID → единственная попытка → engine ID/контур/config hash/fingerprint → batch ID, XML SHA, полное множество message IDs. «Последний файл» и приблизительное имя не используются. Подтверждение MDN на сам ACK независимо от его прикладного содержания.

## Воспроизводимый запуск и остановка

Новый стенд (короткий отдельный каталог; команды из корня PV1). `prepare` откажется перезаписывать существующую конфигурацию. Порты можно выбрать через `--ports`; firewall/NAT не меняются.

```powershell
$stand = Join-Path $env:TEMP 'pv1-as2'
.\.tools\as2-venv\Scripts\python.exe tools/as2_stand.py prepare --root "$stand" --ports 18741 18742
$env:PYTHONUTF8 = '1'
$env:PV_AS2_CONFIG = Join-Path $stand 'config.json'
$env:DATABASE_URL = 'sqlite:///' + (Join-Path $stand 'pv1.db').Replace('\','/')
$env:PV_STORAGE_ROOT = Join-Path $stand 'storage'
.\.venv\Scripts\python.exe -m app.manage init-db
# Только новая синтетическая БД; пароль вводится скрыто, не в командной строке:
.\.venv\Scripts\python.exe -m app.manage bootstrap-admin --login local-as2-admin
.\.tools\as2-venv\Scripts\python.exe tools/as2_stand.py start --root "$stand"
.\.tools\as2-venv\Scripts\python.exe tools/as2_stand.py status --root "$stand"
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 18743
```

Открыть `http://127.0.0.1:18743/as2`. В новой БД сначала нужны синтетический случай, ревизия и локально проверенный артефакт с XML сторонами выше; готовый связанный пример воспроизводит тест ниже. Веб-сервер здесь остаётся в текущем окне, останавливается Ctrl+C; скрытые engine/worker запускаются с Windows `CREATE_NO_WINDOW`.

```powershell
.\.tools\as2-venv\Scripts\python.exe tools/as2_stand.py stop --root "$stand"
# Повторный запуск сохраняет БД, ключи, spool и историю:
.\.tools\as2-venv\Scripts\python.exe tools/as2_stand.py start --root "$stand"
.\.tools\as2-venv\Scripts\python.exe tools/as2_stand.py status --root "$stand"
```

`stop` выставляет stop-file нашим worker и посылает аутентифицированный shutdown двум настроенным engine. Не завершает процессы по имени и не трогает чужие службы. `status` показывает доступность обоих engine и число свежих worker heartbeat. Повторный `start` может добавить второго worker; lease и idempotency защищают очередь. Не удалять spool ради «исправления» неопределённости.

## Миграция, архив, смена сертификата

До изменения фактическая head была `20261111_0034`; добавлена `20261111_0035`. Только после явного выбора нужной **тестовой** БД/хранилища, как выше:

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade 20261111_0035
```

Миграция рабочей базы не выполнялась. Проверена новая временная fixture и отдельное обновление 0034 → 0035 с двумя связанными случаями/реакциями/ревизиями/артефактами; прежние строки и схема сохранены, foreign_key_check пуст. Деструктивный downgrade транспортного архива намеренно запрещён.

Для резервной копии при остановленных созданных процессах нужны: SQLite PV1; всё `PV_STORAGE_ROOT` (включая точный XML и `as2-events`); обе `engine-a/engine.db` и `engine-b/engine.db` с исходящими MIME, inbox и event sequence; версия кода, lock, registry всех использованных версий и публичные сертификаты. Ключи, файлы паролей и control tokens копируются/восстанавливаются отдельно защищённым способом, с исходными правами ОС. Engine ID/история должны восстанавливаться согласованно; при утрате истории PV1 не отправляет вслепую. Проверен рестарт из сохранённого состояния, **не** полное восстановление резервной копии на другой машине.

```powershell
.\.tools\as2-venv\Scripts\python.exe tools/as2_stand.py rotate --root "$stand"
```

Ротация добавляет `local-2` и новый CA/два сертификата; старые файлы, fingerprints и registry version сохраняются. Старое намерение использует прежнюю версию; новый артефакт/намерение может выбрать новую. Приём пытается проверить подходящую сохранённую версию, а не удаляет старый decrypting key. Проверены поздний ответ со старой версией и новое сообщение с новой. Просроченные/недоверенные сертификаты не становятся допустимыми ради позднего ответа. Удаление старых ключей — отдельное решение по сроку хранения, не автоматическая уборка стенда.

## Ограничения и следующее действие

Доказана локальная работа двух экземпляров одного движка на Windows/SQLite с небольшим синтетическим сообщением. Не проверены другой AS2-продукт, РЗН, PostgreSQL, продуктивная сеть/TLS, нагрузка, полный disaster recovery, OCSP/CRL-инфраструктура. Медицинское содержание ACK имитирует тестовый контракт; правила РЗН не заменены им. Локальный лимит сообщения 32 MiB, входящего транспорта 40 MiB; это технические ограничения стенда, не регуляторные пределы.

Для подключения нужны отдельные актуальные основания из АИС/РЗН и решения IT/ФН:

1. Официальные версии профиля R3, XSD со всеми зависимостями, бизнес-правил и словарей, допустимые виды сообщений, в том числе маршрут КИ.
2. Точный ACK-профиль, структура/коды каждого результата, идентификаторы сопоставления, правила отрицательных/повторных/поздних ответов; примеры реального принятия и отклонения.
3. Актуальные настройки каждого контура: AS2 From/To, XML Sender/Receiver и назначение остальных ID, endpoint, MDN callback, ACK endpoint, способ аутентификации, согласованные MIME-типы/алгоритмы и политика повторов.
4. Действующие сертификаты/цепочки доверия, сроки и порядок ротации/отзыва, собственные ключи и защищённое хранение. Старые сертификаты, истёкшие 20.05.2026, не подходят.
5. Согласованный внешний сервер/TLS, обратная доступность MDN/ACK, эксплуатационный мониторинг/резервирование/ответственные, сроки ожидания и эскалации, политика публикации и отдельное подтверждение её результата.
6. Одобрение настроек/заявки каждого контура и отдельное разрешение на реальные испытания. Пример отключённой конфигурации не является такой заявкой.

Следующее действие: получить этот комплект, зафиксировать проверяемый профиль партнёра и согласованный план межсистемных испытаний. До этого продолжать только локальный стенд; не переносить его synthetic ACK/сертификаты/алгоритмы в РЗН как готовую конфигурацию.
