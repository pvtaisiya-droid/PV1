# Приёмка PV1 специалистом ФН: локальный синтетический стенд

Подготовка разработчиком не заменяет вашу приёмку. РЗН и АИС не подключены.
Оба случая, контакты, документы и коды справочников учебные. Коды MedDRA не
подтверждены словарём; общий XSD не доказывает соответствие требованиям РЗН.

## Запуск и вход

Готовый стенд находится в `E:\PV1-UAT-20261117\uat`. Сборка — соседний каталог
`candidate`. Исходный проект на C: сохранён; E: использован из-за заполнения C:.
Откройте PowerShell и один раз задайте пароль обычного входа:

```powershell
& 'E:\PV1-UAT-20261117\uat\password.cmd'
```

Введите пароль дважды, не менее 12 символов. Ввод скрыт, пароль не включён
в исходники, команду или отчёт. Логин — **uat.fn**. Повтор команды явно меняет
пароль этого тестового пользователя; данные случаев не удаляются.

```powershell
& 'E:\PV1-UAT-20261117\uat\start.cmd'
& 'E:\PV1-UAT-20261117\uat\status.cmd'
```

Откройте `http://127.0.0.1:18943/login`, войдите. Удобные ссылки на оба случая
и ожидающие follow-up находятся в `E:\PV1-UAT-20261117\uat\START-HERE.html`.
Повторный start не подготавливает базу заново. Если экземпляр уже активен,
новые процессы не создаются; при частичном запуске выполните status, затем stop
и start. Не удаляйте каталог, чтобы «начать заново»: история должна сохраняться.
Используются .cmd-файлы: менять политику выполнения PowerShell не требуется. Если возникают ограничения запуска,
IT может выполнить указанную внутри короткого .cmd команду непосредственно.

## Один маршрут для каждого из двух случаев

| Случай | Что проверять дополнительно |
|---|---|
| `UAT-REGISTERED` / `uat-registered` | Препараты, реакции, лабораторный результат, первичное сообщение и уточнение описания |
| `UAT-STUDY` / `uat-study` | Название и номер исследования, данные регистрации, ожидаемость и отдельное решение о представлении |

1. Откройте случай по ссылке START-HERE. В карточке перейдите к препаратам,
   реакциям и «Клиническим данным». Убедитесь, что подозреваемый и сопутствующий
   препараты различаются; дозы, показания и связи с реакциями не смешаны.
   Исправьте один текст реакции и название препарата через «Исправить», указав
   учебное основание. Исходный XML/источник правки не должен исчезнуть.
2. В клиническом экране выберите текущую запись анализа → «Исправить».
   Отметьте «Изменить» только у результата, введите `1.5000`; единица остаётся
   отдельным полем. Для проверки контактов выберите блок отправителя: строки вводятся без JSON.
   Контакт первичного источника хранится, но сейчас блокирует выгрузку как
   неподтверждённое соответствие C.2; это нужно разобрать, а не обходить. Пустое поле,
   nullFlavor и частичная дата различаются. Не нужно заполнять отсутствующие
   части даты. Для КИ аналогично уточните название исследования и проверьте
   отдельные поля ожидаемости/решения ФН. Не выводите решение о подаче из одной
   серьёзности события.
3. Сохраните правки с основанием. Зафиксируйте новую ревизию внизу клинического
   экрана. Откройте её: это сохранённый снимок, а не текущая карточка. После
   следующей правки старый снимок должен остаться прежним.
4. Перейдите «Подготовить XML этой ревизии». Для этого стенда введите
   отправителя `SYNTH-SENDER`, получателя `SYNTH-RECEIVER`, назначение
   «Локальная проверка», сценарий «Первичное сообщение» и основание.
   После формирования отдельно прочитайте XSD-результат и диагностические
   замечания, включая невыполненные словарные/региональные проверки. Скачайте
   сохранённый XML. Это **не регистрация подачи**.
5. Откройте локальную очередь AS2, выберите точный артефакт, версию `local-1`
   и укажите основание. Поставьте в очередь один раз. После обновления экрана
   должны отдельно появиться положительный транспортный результат MDN и
   локальный ACK. ACK относится к синтетическому JSON-контракту стенда и
   **не означает принятие РЗН или публикацию**. При задержке сначала посмотрите
   status и историю; не нажимайте повтор вслепую.
6. Перейдите к ожидающему follow-up по START-HERE. Входящие факты, текущие
   значения и связи показаны отдельно. Для каждого повтора выберите конкретную
   существующую запись, новый повтор или «Не применять». Не сопоставляйте только
   по порядку строк. Для компактной первой проверки можно сопоставить блок
   сообщения и описание случая с единственными текущими блоками, а остальные
   повторы явно не применять. Введите основание, просмотрите колонки
   «Текущее / Входящее», подтвердите решения по каждому изменению.
   Ожидается уточнённое описание и дата последней информации; невыбранные
   данные сохраняются, ревизии «до» и «после» доступны. Исходник не изменяется.
7. Подготовьте XML новой ревизии со сценарием follow-up и явно выбранным
   предшествующим артефактом. Выбор предыдущего артефакта не доказывает его подачу.
8. На экране «Подача и публикация» выберите артефакт. Для учебной резервной
   подачи сначала зарегистрируйте решение. Если автоматическая доставка уже
   могла состояться, система должна это показать и не обещать её отмену.
   Затем **имитируйте** ручное действие только в стенде: зарегистрируйте
   фактическое время с поясом, например текущий момент `+03:00`, основание
   «Учебная имитация, в АИС ничего не загружалось» и при наличии учебный номер.
   Номер необязателен; неполное подтверждение должно оставаться видимым.
9. Отдельно зарегистрируйте результат ручной подачи. Для конкретной подачи
   добавьте ручную проверку публикации с синтетическим источником, затем
   исправьте ошибочную отметку новой записью. Предыдущая запись, автор и
   основание должны сохраниться. Не ставьте реальную публикацию РЗН.
10. Назначьте ответственного. Явно задайте учебный срок и основание; не
    воспринимайте его как нормативный расчёт. На `/operations` ознакомьтесь
    с задачей о возможном дубле/публикации, назначьте ответственного или закройте
    с учебным основанием. Закрытие задачи не должно менять ACK или факт публикации.
    Если условие не устранено, оно остаётся видимым. Диагностический ZIP содержит
    техническую последовательность, но не XML, документы пациентов или ключи.

Если форма сообщает об устаревшем состоянии, обновите её и повторно сравните
данные. Не пытайтесь обойти блокировку или одновременно править один случай
в нескольких вкладках. Ошибки сохраняйте как замечания приёмки.

## Как записать замечание и завершить работу

Для каждого замечания достаточно: дата; случай; экран/действие; ожидаемый
результат; фактический результат; важность; ссылка/ID артефакта или ревизии.
Снимок экрана допустим только с этими синтетическими данными. Пароль и ключи
в замечание не включать. Отметьте также шаги, которые вы действительно прошли.
Разработчик не заполняет за вас результат пользовательской приёмки.

```powershell
& 'E:\PV1-UAT-20261117\uat\stop.cmd'
& 'E:\PV1-UAT-20261117\uat\status.cmd'
```

Ожидается отсутствие доступных engine/web и свежих heartbeat. Следующий start
сохраняет историю. Останавливаются только процессы этого стенда.

## Решения IT и внешние испытания

IT утверждает носители/сроки резервного хранения, защищённое хранение отдельного
пароля и ключевого компонента, права учётных записей, RPO/RTO, наблюдение за web,
worker, engine **и самим монитором**. После восстановления исходящая передача
остаётся выключенной, в том числе автоматические ответы; перед возобновлением
нужны остановка прежнего отправителя и сверка событий после точки копии.
Откат — согласованное восстановление, не уничтожающий историю downgrade.

Комплект сертификатов РЗН в предоставленных документах имеется, но истёк
20.05.2026. Обновлённые сертификаты/адреса, реальный ACK, совместимость XML,
MIME и алгоритмов, процедура публикации и разрешение на внешние испытания
проверяются отдельно. Настройки local_stand не переносятся в РЗН как согласованные.
