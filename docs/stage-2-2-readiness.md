## Пользовательский процесс и доказательство

В предпросмотре импорта есть ссылка **«Разбор и история идентификаторов»**. Экран показывает причину блокировки, относящиеся к ней случаи, текущие значения/статус, C.1.1/C.1.8.1 и пространство отправителя из доступных XML, контрольные суммы и защищённую загрузку связанного исходника. Клинические сведения на экран не выводятся. Можно вернуться, оставив вопрос нерешённым.

GET/POST экрана и скачивание источника требуют существующего права `icsr_workflow` (предусмотрено для специалиста ФН и администратора). Одного `view` недостаточно. Сервер проверяет это независимо от кнопки; POST использует CSRF, версию случая и пакета, snapshot Case/Batch/Item/Transmission/Decision и штатную блокировку случая. SQLite сериализует проверку snapshot и запись; уникальность дополнительно обеспечивается БД.

Доказательство — **E2BTransmission, уже связанная с выбранным Case**, её item/batch и доступный XML внутри защищённого хранилища. SHA-256 файла должен совпадать с item и передачей. R3 повторно читается существующим парсером 2.1: нужны однозначные C.1.1, C.1.8.1 и пространство отправителя. Непустые исторические ID должны находиться среди этих исходных ID; входящий источник должен согласовываться с ними. Противоречащий читаемый исторический R3 или ранее разобранный источник останавливает решение. Отсутствующий/неинтерпретируемый дополнительный источник не считается подтверждающим; его недостаток виден на экране.

Назначения подтверждает сотрудник с содержательным основанием (20–4000 символов), а не свободным вводом новых ID. Длина комментария сама по себе не является доказательством. Полученный входящий файл без ранее связанного исторического источника не доказывает идентичность старого случая. Процесс рассчитан на один однозначный XML во входящем пакете.

Семантика ICH/OID/пространства отправителя не изменена относительно [этапа 2.1](stage-2-1-readiness.md) и [README источников](../tests/fixtures/e2b_r3_identity/README.md). `manual-r3-identity-v1` — **внутреннее происхождение ручного решения**, не профиль РЗН и не профиль автоматического парсера. Требование доказательства, область решения и порядок уточнения — техническое решение PV1; региональные Q04/Q05 остаются открытыми.

## Что сохраняется и меняется

Новая `CaseIdentityDecision` содержит Case и его версию до решения, входящий batch, связанную передачу и checksum, прежние/подтверждённые значения, XML-контексты/OID исходного извлечения и версию парсера, item/batch источника, snapshot данных, область действия, основание, автора и серверное время. Case получает подтверждённые текущие ID/пространство и отдельный ручной профиль. Решение, изменение Case и обычный AuditTrail сохраняются одной транзакцией.

XML, normalized JSON, клинические связи и номера случаев не меняются. История решений append-only: миграция запрещает UPDATE/DELETE триггерами; предусмотрены ограничения `(case_id, case_version_before)` и `supersedes_id`. Уточнение основания/доказательства при тех же подтверждённых ID создаёт новую запись, явно заменяющую предыдущую. **Смена уже подтверждённой идентичности здесь запрещена** и требует отдельного расследования; исходная запись остаётся доступной в истории.

После записи вызывается обычный `preview_case`. Оставшийся конфликт блокирует импорт, даже если обоснованная интерпретация одного случая уже сохранена. Автоматического подтверждения импорта, выбора первого кандидата, передачи `case_id` в обход matching или исключения из уникальности нет. При последующем matching ручной профиль требует согласованности последнего решения, текущих ID и доступного исходника с тем же checksum. Утрата/изменение доказательства останавливает сопоставление.

## Границы и продолжение

Без доступного, уже связанного и однозначного R3 исторический случай остаётся непроверенным. Не поддерживаются доказательства из произвольных комментариев/новых загрузок, слияние дублей, перенос импортов, смена подтверждённой идентичности, исправление исторических дат и автоматическое расследование. Несколько входящих XML требуют отдельного разбора; этот экран их не разрешает. История доступна через защищённый экран, отдельного API решений нет.

Следующий разработчик должен сохранить незакоммиченные изменения 2.1/2.2, прочитать оба отчёта и применить 0030 только в выбранном изолированном окружении перед использованием экрана. Для реальных нерешённых конфликтов ответственному ФН нужны исходники и отдельное обоснование; изменение подтверждённой идентичности/объединение потребует самостоятельного задания. S2-08 остаётся частичной, профиль РЗН — предварительным. Готовность исходящего E2B(R3), AS2 или всей ICSR-модели этим этапом не подтверждена.
