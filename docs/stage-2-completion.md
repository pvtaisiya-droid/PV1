## Реализация и пользовательский путь

Структурированный JSON не заменяет связи: parent/product/reaction/patient/literature/narrative/attachment имеют собственные FK. Контракт и код входят в репозиторий; `.tmp-stage-1` не нужен для работы.

- В карточке случая открыть **«Клинические данные»**: `/cases/{case_id}/clinical`. Выбрать блок, добавить либо исправить нужный повтор. Отметить изменяемые поля/связи, указать основание. «Очистить текущее» — явная операция; непомеченные поля не меняются. Архив сохраняет источник и аудит, активные дочерние связи требуют предварительного разбора.

Запись требует версии Case, прав и основания; изменение существующей записи — также её версии. Формы используют тот же writer `clinical_data.save`.

## Ревизии, follow-up и пакет

`pv1-clinical-1` фиксирует Case, пациентские и клинические повторы, реакции/препараты/их дочерние структуры, идентификаторы и решения идентичности, narratives/литературу, вложения, входящие передачи/сообщения, связанные SafetyReport/IncomingRequest и ссылки на них, AuditTrail. Есть автор/основание/время, checksum SHA-256, результат локальных проверок. Для файлов сохраняются устойчивый путь/ID и SHA-256; при создании ревизии доступный файл сверяется. Это снимок ссылок и контрольных сумм, не отдельная система резервного копирования файлов.

Ревизию нельзя изменить/удалить через ORM; для SQLite добавлены UPDATE/DELETE-запреты на уровне БД. Исходник IcsrMessage защищён от изменения/удаления приложением. Техническая `version` строки, монотонный номер ревизии, входящие ID/даты и будущая транспортная попытка — разные понятия. Первичный импорт создаёт ревизию; follow-up сохраняет состояние **до** применения и новое состояние **после**. Ручные правки аудируются, отдельную ревизию пользователь фиксирует явно.

Сопоставление случаев использует защищённые правила 2.1/2.2. Повторы между сообщениями не сопоставляются автоматически по позиции/названию/XML-ID. Решение пользователя сохраняется с основанием. Два входящих повтора нельзя скрыто направить в одну строку; чужие, архивные и несовместимые parent/product/reaction связи запрещены. Рассчитанную причинность нельзя заменить импортированным текстом: для него нужна отдельная оценка.

Отсутствие поля/повтора — **сохранить текущее**, а не удаление. Присутствующий nullFlavor показывается как входящий факт неизвестности и принимается только явно. Очистка/архив — отдельная ручная операция. Изменение текущего случая после предпросмотра вызывает stale; сравниваются версия и хеш полного состава. Несколько ожидающих сообщений одной идентичности требуют основания применения конкретного сообщения следующим; порядок файлов не является порядком follow-up. Локальное ручное решение не подменяет будущие правила Q05.

Граница транзакции — **одно сообщение/случай**, включая связи, аудит, документы, решение и ревизию. Применённое сообщение/план повторно возвращает тот же Case без изменений. Точное совпадение хеша физического XML и выделенного фрагмента с ранее применённым источником отмечается `duplicate`; разные исходники требуют разбора. Ошибка другого ICSR/файла не выдаётся за успех. Пакет остаётся `partially_processed`, пока есть неприменённые/ошибочные сообщения или XML. Автоматического слияния случаев и атомарности всего ZIP нет.

Предлагаемый контракт, **не реализованный отправитель**:

1. Вход сериализатора: `revision_id`, `schema_version=pv1-clinical-1`, SHA-256 снимка; `recipient_id` и `environment` (`test`/`prod`); документально зафиксированные `profile_id/version`, versions справочников и правил; снимок результатов локальных/профильных проверок; подтверждённое решение ФН и основание. Используется сохранённая ревизия, не меняющиеся текущие ORM-строки.
2. Будущий артефакт: точные XML-байты, кодировка/MIME, SHA-256, версия сериализатора, профиль/XSD и хеш комплекта, неизменяемые связи на ревизию и идентификаторы пакета/сообщения/случая. Пока этих артефактов нет. Пересериализация — новый артефакт, а не подмена ранее переданных байтов.
3. Отдельная исходящая передача связывает адресата/контур с артефактом. `E2BTransmission` остаётся входящим журналом. Повтор транспортной попытки не создаёт клиническую ревизию и не определяет follow-up. Правила смены внешних ID после исправления/отказа зависят от Q04/Q05.
4. Каждая будущая транспортная попытка имеет свой ID/время/результат и AS2 Message-ID. MDN (MIC/доставка), прикладной ACK (результат по подтверждённой схеме) и публикация (регистрационный номер/источник подтверждения) хранятся раздельно. Ни один из этих статусов не выводится автоматически из другого.
5. Перед разработкой регионального сериализатора закрыть прикладные Q01–Q06/Q08–Q09 и семантику публикации Q10, зафиксировать принимаемые примеры и набор профильных правил. Q07 нужен для следующего этапа транспорта. Никаких отправок/положительных квитанций/фиктивных XML в этой реализации нет.
