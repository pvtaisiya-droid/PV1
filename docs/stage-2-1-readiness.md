## Реализация

- `app/e2b_r3_identity.py`: отдельный узкий разбор ID/дат. Сохраняются extension без изменения регистра/значимых символов, root, assigningAuthorityName, XML-контекст, исходные кандидаты и версия интерпретации `ich-r3-identity-dates-v1`. Суффикс ID не используется как версия: R3 `message_version=None`.
- `app/e2b_import.py`: проведены значения через парсер, normalized JSON, предпросмотр, подтверждение и E2BTransmission. JSON содержит ссылку на batch/item/checksum; исходный XML остаётся сохранённым. Порядок ID не определяет назначение. Исправлено распознавание непосредственно корневого PORR с подчёркиванием в имени.
- `find_existing_case`/`preview_case`: проверяются все XML пакета и все кандидаты. Локальный ID сопоставляется в точном пространстве отправителя N.2.r.2 (root + extension), включая ранее сохранённые источники этого случая. Конфликт worldwide/local, несколько кандидатов, неоднозначный контекст, неизвестное пространство или пересечение непроверенных исторических ID останавливают автоматическое объединение. Изменение ID уже известного отправителя также требует разбора. Значения ID/медицинские данные не включены в тексты новых ошибок.
- C.1.4/C.1.5 хранят `raw`, `parsed`, проекцию полного дня `value`, `precision`, `timezone`, `null_flavor`, `state`, исходные атрибуты и контекст. Состояния: `missing`, `null_flavor`, `partial`, `parsed`, `invalid`, `ambiguous`. Год/месяц не достраиваются; неизвестность и ошибка разбора не заменяются today. Дробные секунды/пояс остаются в исходном и разобранном представлении. Полученный nullFlavor сохраняется без заявления о допустимости для отправки.
- `Case.initial_received_date`/`latest_received_date` и `SafetyReport.received_date` — только проекции известных полных дат. `SafetyReport.received_at`, created_at/imported_at остаются внутренними timestamps. Обязательная учётная дата IncomingRequest для нового R3 означает регистрацию в PV1; это назначение явно возвращается как `received_date_basis` и подписано в интерфейсе. Связанные пути ручного создания случая/привязки follow-up больше не подставляют эту учётную дату вместо исходной.
- `models.py`, `schemas.py`: новые nullable `Case.e2b_identity_profile` и `e2b_sender_scope`; существующий normalized JSON и связи использованы для фактов, без универсальной таблицы provenance. CaseRead/SafetyReportRead возвращают `e2b_source_facts` с источником и регистрацией. Содержательные версии всех данных не создавались.
- `routers/safety_reports.py`, `_e2b_source_facts.html`, `e2b_import_preview.html`, `case_detail.html`, `safety_report_detail.html`: компактный блок ID/дат и предупреждений; при конфликте кнопка импорта отключена, а сервер независимо повторяет проверку. `crud.py`, `routers/incoming_requests.py`, `incoming_requests.html`, `incoming_case_preview.html` затронуты только для назначения учётной даты и предотвращения её обратной подстановки. Проверки прав, snapshot/expected version, блокировки и транзакции сохранены.

Редактор исходных E2B-фактов не добавлен. Исходный факт доступен отдельно от текущего поля карточки; существующие механизмы ручного ввода/аудита не заменены. Отдельное подтверждение исторической интерпретации с автором и основанием — следующая задача.
