# Эксплуатация PV1 и согласованное восстановление

Актуальный локальный процесс этапов 5–6, обновлено 17.11.2026. Только синтетический
`local_stand`; РЗН test/prod остаются выключены. Результаты и ограничения —
[stage-5-readiness.md](stage-5-readiness.md), приёмка —
[stage-5-acceptance.md](stage-5-acceptance.md).
Ни скачивание, ни MDN, ни локальный ACK не подтверждают публикацию.

## Ответственные и подготовка экземпляра

ФН отвечает за содержательную ревизию, адресата, явный срок/основание,
решение о резервной подаче, доказательства, разбор дублей и ручную публикацию.
IT отвечает за установку, собственные процессы, доступы, сертификаты,
согласованную копию/восстановление и недопущение второго активного отправителя.
Владелец системы утверждает пороги, владельцев задач, расписание контроля,
RPO/RTO, срок хранения, отдельный носитель и хранение пароля восстановления.

Новый экземпляр устанавливается из выбранного проверенного дерева кода, а не
из исторического HEAD. Для нового окружения использовать совместимый Python
3.12 и фиксированные зависимости (на существующем окружении без необходимости
не переустанавливать):

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.lock.txt
python -m venv .tools/as2-venv
.\.tools\as2-venv\Scripts\python.exe -m pip install --only-binary=:all: --require-hashes -r tools/as2-requirements.lock.txt
```

`python` здесь должен быть проверенным установленным 3.12, не псевдонимом
WindowsApps. Первоначальная установка уже проверена этапом 0; повторять её
ради эксплуатации не требуется. Перед импортом приложения всегда задавать пути.
Пример **нового синтетического** экземпляра, из корня проекта:

```powershell
$stand = 'C:\PV1Lab\acceptance-01' # новый короткий каталог; не рабочая БД
$env:PYTHONUTF8='1'
$env:DATABASE_URL='sqlite:///'+($stand.Replace('\','/')+'/pv1.db')
$env:PV_STORAGE_ROOT="$stand\storage"
$env:PV_AS2_CONFIG="$stand\config.json"
Remove-Item Env:PV_RESTORE_PATH_MAP -ErrorAction SilentlyContinue
.\.tools\as2-venv\Scripts\python.exe tools/as2_stand.py prepare --root "$stand" --ports 18741 18742
.\.venv\Scripts\python.exe -m app.manage init-db
.\.venv\Scripts\python.exe -m app.manage bootstrap-admin --login local-operations-admin
```

Последняя команда интерактивно создаёт/восстанавливает только локального
администратора выбранной базы. Пароль не помещать в команды/отчёты/Git.
Реальные сведения и сертификаты компании здесь не использовать.
Для обновления существующего экземпляра: сначала offline-копия ниже,
затем установка согласованного дерева/зависимостей, явные пути и
`python -m alembic upgrade 20261112_0036` соответствующим app-интерпретатором.
На восстановленной базе никогда не выполнять повторную инициализацию.

## Запуск, остановка и наблюдение

```powershell
.\.tools\as2-venv\Scripts\python.exe tools/as2_stand.py start --root "$stand"
.\.tools\as2-venv\Scripts\python.exe tools/as2_stand.py status --root "$stand"
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 18743
```

`start` запускает два движка, worker и независимый монитор без видимых окон.
Не вызывать `start` многократно для уже работающего экземпляра; сначала проверить
status и сохранённые `last-start.json`/heartbeat. Web работает в текущем окне.
Для остановки web — Ctrl+C в его окне, затем:

```powershell
.\.tools\as2-venv\Scripts\python.exe tools/as2_stand.py stop --root "$stand"
.\.tools\as2-venv\Scripts\python.exe tools/as2_stand.py status --root "$stand"
```

Stop-файл останавливает worker/монитор, движки получают аутентифицированную
команду. При недоступном процессе сверять PID и командную строку из запуска;
не завершать все python/службы по имени. Дождаться выхода перед backup;
его блокировки дополнительно отклоняют активную среду.

Проверка работоспособности: `/health`, обычный вход, `/operations`, `/as2`,
свежий heartbeat worker и доступность обоих control API. Один `/health`
не доказывает обработку очереди. Монитор опрашивает примерно раз в 15 секунд;
внешнее наблюдение за **самим монитором** и дежурство IT нужно назначить отдельно.

На `/operations` администратор сохраняет новую версию политики для версии
контура: ответственный, ожидания MDN/ACK/публикации, приближение срока,
предупреждение сертификатов, heartbeat, интервал и предел повторных напоминаний,
известная автопубликация и основание. Политика без сохранения не действует.
30/60 секунд — параметры синтетического стенда, не условия РЗН.
Пороги исторического транспортного снимка на `/as2` не переписываются;
эксплуатационные задачи используют выбранную текущую версию `OpsPolicy`.

## Разбор ответов, неопределённость и ручная подача

1. Выбрать точный артефакт/ревизию/SHA в карточке → «Ревизии и XML» →
   «Ручная подача и публикация». Новая очередь создаёт эксплуатационный учёт
   сама. Для старого намерения явно открыть учёт его артефакта, не подтверждая
   старую подачу задним числом. Проверить адресата/версию и назначить ответственного.
2. Указать срок конкретного сообщения и документированное основание. Дата
   `YYYY-MM-DD` не становится полуночью; точное время требует `+03:00` или `Z`.
   Нормативный срок не вычисляется из серьёзности. 72 часа R1 §4 P102 — описание
   возможной задержки, а не разрешение нарушить более ранний срок сообщения.
3. При отсутствующем MDN проверить доступность, историю attempt/engine и
   несопоставленные ответы. При отрицательном MDN — доверие/коды ошибки и
   криптографическую проверку. При отсутствии/отказе ACK — отдельно разобрать
   прикладной результат. Сохранённые raw/payload доступны через защищённые маршруты;
   не пересылать их в обычном диагностическом пакете.
4. `unknown`, `delivery_possible`, несопоставленный/противоречивый ответ не
   разрешают повтор. Сверить технические ID и доказательства; сверка движка
   не создаёт новое сообщение. Повтор разрешён прежним механизмом только при
   подтверждённом сбое до доставки; ручной hold его блокирует.
5. Для резервной подачи сначала записать **решение** с основанием. Проверить
   `pv1_stopped`/`engine_stopped` либо предупреждение о возможной прежней доставке.
   `engine_pending` требует действий IT и не означает отмены. Приёмник не выключать.
6. Скачать точный XML. Это только скачивание. Ручную загрузку в АИС выполняет
   сотрудник вне PV1. Затем отдельно зарегистрировать фактическое время с поясом,
   основание, известный номер и/или защищённое доказательство. Номер не выдумывать;
   неполное подтверждение останется задачей. Отдельно добавить полученный результат.
7. Поздний ACK/MDN сохраняется по исходной попытке. Ручной факт остаётся.
   Возможный дубль/конфликт разбирает ФН; «последний» результат автоматически
   не выбирается. Подтверждение ознакомления, назначение и закрытие задачи
   сохраняются. Закрытие с оставшимся условием не делает отсутствующий ACK положительным.

## Публикация и безопасная диагностика

Для каждой конкретной подачи отдельно зарегистрировать проверку: источник,
основание/доказательство, сотрудник, результат; время публикации/номер — только
если известны. Результат всегда обозначен как ручной. Ошибка исправляется
новой записью, сохраняющей предыдущую. При выключенной автопубликации сотрудник
должен выполнить действие в АИС; при включённой всё равно нужно доказательство.
Сама настройка в АИС через PV1 не меняется.

Диагностический ZIP скачивается на экране сообщения с правами `view`/`export`
и основанием; действие аудируется. По умолчанию это только техническая
allowlist, без XML, медицинского содержимого ACK, свободного текста/ссылок,
секретов, БД и логов. Проверять назначение пакета перед передачей: его технические
идентификаторы всё равно являются служебной информацией. Автоматической отправки нет.

## Ротация сертификатов

IT проверяет публичные сроки и отпечатки по версии конфигурации; ФН учитывает
влияние на сообщения в ожидании. Сначала backup, остановка собственных писателей,
новая версия конфигурации, проверка доверия/адресата, затем запуск и целевой
синтетический обмен. Старые версии, ключи и попытки не удалять — они нужны для
истории/поздних ответов. Для **локального стенда**:

```powershell
.\.tools\as2-venv\Scripts\python.exe tools/as2_stand.py rotate --root "$stand"
```

Эта команда генерирует новую локальную тестовую цепочку; это не процедура
выпуска сертификата РЗН. Не использовать её на восстановленном fenced экземпляре
для снятия запрета. Старые сертификаты из документов 2025–2026 не являются
актуальной конфигурацией. С этапа 6 проверка архива отделена от допуска к живому обмену. Истёкший
сертификат не запрещает восстановить данные: проверяются подписи цепочки
локального профиля, BasicConstraints/KeyUsage, отпечатки, пароль и соответствие
закрытых ключей. В restore-report записываются сроки и состояние каждого
сертификата (current/expired/not_yet_valid), без подмены времени проверки.
Повреждение, подмена и неверный ключ/пароль по-прежнему вызывают отказ.
Исторические результаты MDN/ACK не переоцениваются этой проверкой. Живой обмен
по-прежнему требует действительных сертификатов. Ротация и перезапуск сохраняют
исходящий recovery-запрет, включая автоматические ответы.

## Согласованная offline-копия интеграции

Остановить **все собственные** web/worker/monitor/engine/импортёры выбранного
экземпляра, запретить стороннюю запись в storage. Задать явные проверенные пути.
Обычная копия SQLite не заменяет этот комплект. Пример из корня проекта:

```powershell
$repo=(Get-Location).Path
$snapshot='C:\PV1Lab\backups\acceptance-01-20261112' # новый каталог
$secret='C:\PV1Vault\acceptance-01-20261112.keys' # отдельно, права только владельцу
.\.tools\as2-venv\Scripts\python.exe tools/backup_snapshot.py integration-create --root "$repo" --database "$stand\pv1.db" --storage "$stand\storage" --config "$stand\config.json" --destination "$snapshot" --secret-output "$secret" --offline
.\.tools\as2-venv\Scripts\python.exe tools/backup_snapshot.py integration-verify "$snapshot"
```

Пароль восстановления (не менее 16 символов) вводится скрыто дважды, хранится
отдельно утверждённым владельцем способом. Не писать его в argv, `.ps1`, архив
или отчёт. Ключевой компонент зашифрован AES-256-GCM/Scrypt, отдельно от обычной
копии. Копия содержит медицинские данные и тоже требует защищённого носителя/ACL;
диагностический ZIP её не заменяет. Копировать проверенный комплект на отдельный
носитель по политике владельца. Срок хранения, расписание и RPO/RTO не назначены
кодом. Потеря пароля/компонента делает полное восстановление невозможным.

Команда использует общий runtime lock, эксклюзивные блокировки движков,
резервирование записи всех трёх SQLite, backup API и проверку состава/SHA.
Активная/меняющаяся среда или внешняя/отсутствующая файловая ссылка вызывает
отказ. Нельзя считать незавершённый каталог копией; его не удаляют автоматически.
Это offline-механизм, не обещание online-consistent backup.

## Восстановление и возврат после неудачного обновления

Восстанавливать только в новый каталог с другими loopback-портами, не поверх
источника. Остановить/изолировать исходного отправителя. Для репетиции исходный
стенд не удалять. Из текущего дерева, используя существующий engine-интерпретатор:

```powershell
$appPython=(Resolve-Path '.venv\Scripts\python.exe').Path
$enginePython=(Resolve-Path '.tools\as2-venv\Scripts\python.exe').Path
$restored='C:\PV1Lab\restored-01' # должен отсутствовать
& $enginePython tools/backup_snapshot.py integration-restore --snapshot "$snapshot" --destination "$restored" --secret-component "$secret" --ports 18751 18752
Set-Location "$restored\source"
$env:DATABASE_URL='sqlite:///'+($restored.Replace('\','/')+'/pv1.db')
$env:PV_STORAGE_ROOT="$restored\storage"
$env:PV_AS2_CONFIG="$restored\config.json"
$env:PV_RESTORE_PATH_MAP="$restored\path-map.json"
& $enginePython tools/as2_stand.py start --root "$restored" --app-python "$appPython"
& $enginePython tools/as2_stand.py status --root "$restored"
& $appPython -m uvicorn app.main:app --host 127.0.0.1 --port 18753
```

Повторный запуск восстановленного экземпляра всегда использует эти четыре
переменные и восстановленный `source`. В примере повторно используются
установленные интерпретаторы с подходящими lock-версиями; на другом хосте
IT создаёт окружения из сохранённых lock-файлов. Не запускать код исторического
HEAD вместо сохранённых незакоммиченных исходников.

Проверить `restore-report.json`, manifest SHA, DB integrity/FK, файлы/ссылки,
engine ID/sequence, обычный вход, прежние ревизии/XML/ответы и ручную историю.
`path-map.json` перенаправляет старые абсолютные ссылки только в новый storage;
нет fallback к старому каталогу. Ключи расшифровываются только в защищённый
каталог восстановленного экземпляра и проверяются с публичными сертификатами.

По умолчанию `runtime.outgoing_disabled=true`: worker не захватывает отправку,
engine не принимает новую send и не выполняет исходящие задания, включая ACK.
`source_fenced=false` честно означает, что инструмент не может доказать остановку
другого хоста. Приём/история доступны, но восстановленная копия не становится
вторым отправителем. `unknown` нельзя превращать в queued или success.

Возврат после неудачного обновления — восстановление согласованной копии
кода+БД+storage+engine+ключей; запрещённый downgrade не является откатом.
После точки копии получатель мог получить новые сообщения: IT/ФН сверяют эту
историю отдельно, подтверждают прекращение отправки исходным экземпляром и
решают судьбу каждого неопределённого/устаревшего задания. **Не снимать глобальный
запрет вручную ради автоматической пересылки всей очереди.** Автоматического
release после восстановления нет; для возобновления нужен отдельный согласованный
контроль включения и межсистемная сверка. До этого доступны чтение, разбор и
управляемый ручной канал.

Остановить восстановленный web в его окне, затем `tools/as2_stand.py stop --root
"$restored"` соответствующим engine-интерпретатором из восстановленного source.
Репетиция этапа 5 выполнила этот процесс; этап 6 дополнительно подтвердил
реальное восстановление с истёкшей синтетической цепочкой и сохранение запрета
после ротации. Продуктивную сеть, иной хост, RPO/RTO и согласованное включение
после аварии принимает IT отдельно. Повторно архив не подтверждает подписи квитанций.


## Версия для пользовательской приёмки и её обновление

Инструкция ФН: [user-acceptance.md](user-acceptance.md); фактические доказательства:
[stage-6-readiness.md](stage-6-readiness.md). Собрать исходный кандидат из
проверенного текущего дерева (Git HEAD сам по себе недостаточен):

```powershell
.\.venv\Scripts\python.exe tools/acceptance_bundle.py build E:\PV1-UAT-20261117\candidate
.\.venv\Scripts\python.exe tools/acceptance_bundle.py verify E:\PV1-UAT-20261117\candidate
```

Первую команду не повторять поверх существующего каталога: для новой версии
нужно новое имя. Manifest фиксирует dirty/HEAD, build ID и SHA всех исходников;
кэши Python, возникающие при чтении установленного кода, не являются исходниками.
База, storage, ключи и окружения в candidate не входят. Сохранённый каталог source
не требует исходного рабочего дерева или .git для запуска. Окружения зависимостей
могут быть установлены отдельно по включённым lock-файлам; не помещать их в source.

Для нового стенда (команда отказывается перезаписывать каталог):

```powershell
$appPython='C:\Users\skreshchanovskaia\Documents\ChatGPT\ФН разработка\PV1\.venv\Scripts\python.exe'
$enginePython='C:\Users\skreshchanovskaia\Documents\ChatGPT\ФН разработка\PV1\.tools\as2-venv\Scripts\python.exe'
& $appPython E:\PV1-UAT-20261117\candidate\source\tools\acceptance_stand.py prepare --root E:\PV1-UAT-20261117\uat --engine-python $enginePython --ports 18941 18942 18943
```

На другом хосте заменить пути интерпретаторов соответствующими установленными
окружениями. Password/start/status/stop.ps1 создаются внутри стенда с точными
путями; не содержат пароля. При изменении пути/версии bundled Python после
обновления desktop-приложения IT должен проверить интерпретатор до запуска;
не переустанавливать весь стек без необходимости.

Обновление выбранного экземпляра: остановить его процессы; создать и проверить
согласованную offline-копию integration-create; установить **новый** candidate и
проверить manifest; сохранить прежний код/конфигурации/ключи; явно задать DATABASE_URL,
PV_STORAGE_ROOT, PV_AS2_CONFIG и, если применимо, PV_RESTORE_PATH_MAP; запустить
`python -m app.manage upgrade-db` из нового source подходящим app-интерпретатором.
В этапе 6 схема не менялась (0036). Затем обновить только пути запуска этого
экземпляра, запустить и проверить вход/данные/worker/engine/монитор и историю.
Подготовку prepare поверх существующего экземпляра не выполнять.
Перенос состояния при возврате — только описанный выше согласованный restore,
с выключенной передачей и сверкой сообщений после точки копии. Этот порядок
на рабочей базе в этапе 6 не выполнялся.

## Прежний формат 1: только PV1 SQLite и хранилище

Ниже сохранена инструкция прежнего инструмента. Она применима к отдельному
PV1 без полной AS2-интеграции; её `create/restore` **не являются** согласованной
копией двух движков и не заменяют команды `integration-*` выше.

`tools/backup_snapshot.py` сохраняет SQLite через backup API, всё файловое
хранилище и отобранные исходники текущей рабочей папки, включая новые файлы.
Приложение не импортируется, сервер и миграции не запускаются. Исходная база
открывается только через `mode=ro`. Команды выполняются из корня проекта.

Перед созданием копии остановите сервер, импортёры и другие процессы записи.
`--offline` подтверждает это условие; сам скрипт процессы не останавливает.
Скрипт сравнивает SHA-256 базы/WAL и хранилища до и после копирования, но это
дополнительная проверка, а не замена остановке всех писателей.
Определите фактические `DATABASE_URL` и `PV_STORAGE_ROOT` с учётом окружения,
`.env` и рабочего каталога процесса. По умолчанию это `pv_system.db` и `uploads`.
Пути задаются явно; отсутствующие источники и существующий каталог назначения
вызывают отказ. Для каждой новой копии используйте новое имя каталога.

```powershell
.\.venv\Scripts\python.exe tools/backup_snapshot.py create --root C:\Codex\PV1 --database C:\Codex\PV1\pv_system.db --storage C:\Codex\PV1\uploads --destination C:\Codex\PV1\backups\audit-20261001-step1 --offline
.\.venv\Scripts\python.exe tools/backup_snapshot.py verify C:\Codex\PV1\backups\audit-20261001-step1
.\.venv\Scripts\python.exe tools/backup_snapshot.py restore C:\Codex\PV1\backups\audit-20261001-step1 C:\Codex\PV1\.tmp-audit-step1-restore
```

Состав копии:

- `database.sqlite3` — согласованный снимок SQLite, включая committed WAL;
- `storage/` — всё хранилище, в том числе пока не связанные с базой файлы;
- `source/` — приложение, статические ресурсы, Alembic, `migration_support`,
  тесты, lock-файлы, команды запуска, документация, примеры и Python-утилиты;
- `manifest.json` — SHA-256 и размеры файлов, исходные пути, Git HEAD,
  состояние рабочей папки и перечень файлов, исключённых из исходников;
- `recovery-report.json` — ревизия, число строк по таблицам, результаты
  `integrity_check`, `foreign_key_check` и проверка каждой файловой ссылки.

Из исходников исключены `.env`, базы, логи, временные результаты, выгрузки CSV,
архивы импорта и отчёты JSON. Секреты конфигурации при наличии нужно сохранять
отдельно защищённым способом. Внешние файлы за пределами указанного хранилища
автоматически не копируются: каждая такая ссылка отмечается `outside_storage`.
`original_path` и `technical_path` E2B обозначают пути внутри архива/XML и не
считаются ссылками на файлы диска. Проверяются также удалённые записи и версии.

Коды завершения: **0** — состав, база и ссылки проверены; **2** — копия создана
или восстановлена, но есть отсутствующие/внешние ссылки либо нарушения базы;
**1** — ошибка копирования, изменение источника или несовпадение контрольных
сумм. При ошибке незавершённый каталог сохраняется для разбора; без манифеста
его нельзя использовать как подтверждённую копию. Подробности с идентификаторами
записей остаются в локальном отчёте, в консоль выводятся только счётчики.

Восстановление копирует данные в **новый** каталог и повторно сверяет все файлы
и базу. Рабочие данные и пути внутри базы не переписываются. Для проверки ссылки
пересчитываются от исходного корня к восстановленному `storage/`, поэтому наличие
файла в рабочем хранилище не может скрыть потерю в копии.

Это проверка восстановления данных, а не запуск восстановленного приложения.
В базе могут оставаться абсолютные исходные пути. Перед запуском на другом пути
нужен отдельный проверенный перенос ссылок на восстановленное хранилище и явные
`DATABASE_URL`/`PV_STORAGE_ROOT`; до этого сервер на восстановленной базе
запускать нельзя. Нельзя выполнять `init-db`/миграции поверх архивного снимка.
При необходимости создайте ещё одну экспериментальную копию. Исходный снимок
сохраняет историческую схему; её обновление проверяется отдельно в шаге 7.

Каталоги `backups/audit-*` исключены из Git. Копия на том же диске подходит для
проверки отката изменений, но не защищает от потери диска: для эксплуатации
нужно перенести проверенный комплект на отдельный защищённый носитель.

Для известных шаблонных ссылок импорта Access зафиксировано
[исходное состояние](access-attachment-baseline.md). Его проверяет
`python -m tools.audit_access_attachments`; отчёт сохраняется вне снимка.
Объяснение происхождения ссылки не отменяет код 2 проверки восстановления
и не означает наличие самого файла. Новые снимки должны сохранять эти
пропуски в `recovery-report.json`, пока реальные файлы не будут получены.
