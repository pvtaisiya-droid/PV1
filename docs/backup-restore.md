# Резервная копия и пробное восстановление SQLite

`tools/backup_snapshot.py` сохраняет SQLite через backup API, всё файловое
хранилище и отобранные исходники текущей рабочей папки, включая новые файлы.
Приложение не импортируется, сервер и миграции не запускаются. Исходная база
открывается только через `mode=ro`. Команды выполняются из корня проекта.

Перед созданием копии остановите сервер, импортёры и другие процессы записи.
`--offline` подтверждает это условие; сам скрипт процессы не останавливает.
Скрипт сравнивает SHA-256 базы/WAL и хранилища до и после копирования, но это
дополнительная проверка, а не замена остановке всех писателей.
Определите фактические `DATABASE_URL` и `PV_STORAGE_ROOT` с учётом окружения,
`.env` и рабочего каталога процесса. По умолчанию это `pv_system.db` и `uploads`.
Пути задаются явно; отсутствующие источники и существующий каталог назначения
вызывают отказ. Для каждой новой копии используйте новое имя каталога.

```powershell
.\.venv\Scripts\python.exe tools/backup_snapshot.py create --root C:\Codex\PV1 --database C:\Codex\PV1\pv_system.db --storage C:\Codex\PV1\uploads --destination C:\Codex\PV1\backups\audit-20261001-step1 --offline
.\.venv\Scripts\python.exe tools/backup_snapshot.py verify C:\Codex\PV1\backups\audit-20261001-step1
.\.venv\Scripts\python.exe tools/backup_snapshot.py restore C:\Codex\PV1\backups\audit-20261001-step1 C:\Codex\PV1\.tmp-audit-step1-restore
```

Состав копии:

- `database.sqlite3` — согласованный снимок SQLite, включая committed WAL;
- `storage/` — всё хранилище, в том числе пока не связанные с базой файлы;
- `source/` — приложение, статические ресурсы, Alembic, `migration_support`,
  тесты, lock-файлы, команды запуска, документация, примеры и Python-утилиты;
- `manifest.json` — SHA-256 и размеры файлов, исходные пути, Git HEAD,
  состояние рабочей папки и перечень файлов, исключённых из исходников;
- `recovery-report.json` — ревизия, число строк по таблицам, результаты
  `integrity_check`, `foreign_key_check` и проверка каждой файловой ссылки.

Из исходников исключены `.env`, базы, логи, временные результаты, выгрузки CSV,
архивы импорта и отчёты JSON. Секреты конфигурации при наличии нужно сохранять
отдельно защищённым способом. Внешние файлы за пределами указанного хранилища
автоматически не копируются: каждая такая ссылка отмечается `outside_storage`.
`original_path` и `technical_path` E2B обозначают пути внутри архива/XML и не
считаются ссылками на файлы диска. Проверяются также удалённые записи и версии.

Коды завершения: **0** — состав, база и ссылки проверены; **2** — копия создана
или восстановлена, но есть отсутствующие/внешние ссылки либо нарушения базы;
**1** — ошибка копирования, изменение источника или несовпадение контрольных
сумм. При ошибке незавершённый каталог сохраняется для разбора; без манифеста
его нельзя использовать как подтверждённую копию. Подробности с идентификаторами
записей остаются в локальном отчёте, в консоль выводятся только счётчики.

Восстановление копирует данные в **новый** каталог и повторно сверяет все файлы
и базу. Рабочие данные и пути внутри базы не переписываются. Для проверки ссылки
пересчитываются от исходного корня к восстановленному `storage/`, поэтому наличие
файла в рабочем хранилище не может скрыть потерю в копии.

Это проверка восстановления данных, а не запуск восстановленного приложения.
В базе могут оставаться абсолютные исходные пути. Перед запуском на другом пути
нужен отдельный проверенный перенос ссылок на восстановленное хранилище и явные
`DATABASE_URL`/`PV_STORAGE_ROOT`; до этого сервер на восстановленной базе
запускать нельзя. Нельзя выполнять `init-db`/миграции поверх архивного снимка.
При необходимости создайте ещё одну экспериментальную копию. Исходный снимок
сохраняет историческую схему; её обновление проверяется отдельно в шаге 7.

Каталоги `backups/audit-*` исключены из Git. Копия на том же диске подходит для
проверки отката изменений, но не защищает от потери диска: для эксплуатации
нужно перенести проверенный комплект на отдельный защищённый носитель.

Для известных шаблонных ссылок импорта Access зафиксировано
[исходное состояние](access-attachment-baseline.md). Его проверяет
`python -m tools.audit_access_attachments`; отчёт сохраняется вне снимка.
Объяснение происхождения ссылки не отменяет код 2 проверки восстановления
и не означает наличие самого файла. Новые снимки должны сохранять эти
пропуски в `recovery-report.json`, пока реальные файлы не будут получены.
