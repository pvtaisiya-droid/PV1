## Реализация и источник истины

| Сущность | Изменение |
|---|---|
| CaseProduct | Роль, исходное имя и каталог раздельны; кодированные ID с системами/версиями; авторизация; неизменяемые исходные факты. Новый R3 не записывает первый режим/показание в старые одиночные поля. |
| CaseDrugDosage (новая) | Независимые режимы: доза либо отношение, числовая лексика/единицы, интервал, текст частоты, начало/конец raw/nullFlavor, длительность, описание, форма, серия, путь пациента/родителя с кодами и версиями. Точность, часовой пояс и состояние даты читаются через provenance. |
| CaseDrugIndication (новая) | Повторы текста показания, LLT и версии, nullFlavor; исторический PT хранится отдельно как legacy_meddra_pt_code, не становится LLT. |
| CaseDrugSubstance | Расширена существующая сущность: исходный идентификатор/система/версия, числитель и знаменатель содержания с единицами, provenance. Автоматическое сопоставление R3-вещества по имени не выполняется. |
| CaseProductReactionAssessment | Расширена существующая сущность: источник/текст метода/результат и provenance. Несколько оценок одной пары сохраняются. Импорт имеет causality_method=imported_text; новый произвольный ручной метод — manual_text. Существующие WHO-UMC/Naranjo и их расчёты не менялись. Расчётную оценку нельзя переписать свободным текстом через новый редактор; можно создать отдельную оценку, сохранив прежнюю. |
| CaseDrugRechallenge (новая) | Самостоятельные записи пары препарат–реакция с кодом/системой/версией/nullFlavor. «Назначен, реакция не повторилась», «назначен, результат неизвестен», «не назначен/неприменимо» не смешиваются. |

**Текущая доза и показания — дочерние записи.** Старые scalar-поля CaseProduct остаются историческим снимком, не редактируются новым PATCH/формами и не подменяют текущие повторы на вкладке препарата. Старые маршруты добавления одиночного препарата и первичная ручная карточка создают первоначальный дочерний режим/показание один раз. Совместимость R2 сохраняет его исходные одиночные значения и дополнительно переносит их в дочерние записи с `r2_single_unverified`. Общий text веществ старого ввода остаётся историческим текстом, не разбирается по запятым в подтверждённый состав. Путь введения из каталога автоматически не подставляется в режим.

Источник нового R3: `source_facts_json` содержит XML-поддерево, контекст, исходные атрибуты и индекс повтора, ссылку `import_source` на batch/item/checksum. XML ID реакций добавлены в их факты только для точного разрешения связей. Исходные item XML/normalized JSON и факты не меняются при ручной правке; `reviewed_fields_json` обозначает изменённые поля, AuditTrail хранит автора, основание, старое/новое значение. Профиль исходной записи после правки не становится «полностью проверенным». Неподдержанные коды/nullFlavor остаются доступными в фактах, это не разрешение их отправки. Невалидное число из XML остаётся исходной строкой с предупреждением; ручной структурированный числовой ввод требует конечного числа. Единицы не пересчитываются.

Неоднозначные/чужие XML-ссылки и неоднозначная структура одиночных элементов режима блокируют подтверждение, пакет остаётся для разбора. Несколько неоднозначных дат сохраняются в source_facts с предупреждением без выбора «первой». Старый предпросмотр без нового профиля препарата требует перепроверки исходника. Неизвестная историческая роль остаётся прежней при правке другого поля формы; новая роль задаётся явно.

## Пользовательский путь и защита

- Вкладка «Препарат» карточки → `/cases/{case_id}/drug-products`. Показаны текущие повторы, связи с реакциями, состояния дат, непроверенное сопоставление и раскрываемые исходные сведения. Исторический rechallenge препарата обозначен как значение с неустановленной парой.
- `/cases/{case_id}/drug-editor/{kind}` — добавление/исправление `product`, `dosage`, `indication`, `substance`, `assessment`, `rechallenge`. Для правки обязательное основание не короче 10 символов. Формы содержат CSRF и версии.
- API `GET/POST /api/cases/{case_id}/drug-products`; `GET/PATCH .../{product_id}`; `POST .../{product_id}/{kind}`; `PATCH .../{product_id}/{kind}/{row_id}`. GET препарата возвращает все активные дочерние записи. Обычный overview также расширен схемами чтения.
- Для API-записи нужны `expected_case_version`, для дочерней — также `expected_parent_version`, для правки — `expected_version`. Пропущенное поле PATCH сохраняется, явный null очищает только его. Связь существующей оценки/rechallenge нельзя переназначить другой реакции: создаётся отдельная запись с историей.
- `POST .../{product_id}/{kind}/{row_id}/archive` (API и HTML) мягко архивирует дочернюю запись с основанием/автором, без удаления источника и FK. Новое активное чтение исключает её, аудит и физическая запись остаются.
- Используются существующие permissions view/create/edit/soft_delete, `assert_case_editable`, версии SQLAlchemy и `atomic_write`; CASE_INPUTS включает новые дочерние сущности. Подмена case/product/child/reaction ID отклоняется. Никаких дампов исходного XML в обычный журнал не добавлено.

**Follow-up:** новый клинический импорт R3 допускается только для нового случая из одного XML. Для найденного существующего случая и нескольких XML подтверждение останавливается до записи клинических данных. Предпросмотр предупреждает об ограничении; источник сохраняется. Механизмы сопоставления и ручного решения ID этапов 2.1–2.2 не переписаны. Полное клиническое обновление и неизменяемые содержательные версии требуют отдельного этапа S2-08; R2 follow-up не расширялся.
