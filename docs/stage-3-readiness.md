## Пользовательский путь и API

В карточке случая открыть **«Подготовить R3 из ревизии»** (`/cases/{case_id}/r3-export`), выбрать существующую ревизию. Если её нет — зафиксировать её в существующем клиническом экране. Ввести XML ID отправителя/получателя, назначение (`local_test` / `manual_preparation`), сценарий и основание подготовки. Нажать «Проверить, сформировать и сохранить».

Страница показывает ревизию и SHA, параметры конверта, профиль, результат XSD, ошибки/предупреждения/непроведённые проверки с правилом, версией, источником, элементом и конкретным повтором. Решения ФН (`pv_decision`) показаны отдельно. При блокирующих ошибках сохраняется диагностический результат без готового скачивания; исправление выполняется обычным редактором и новой ревизией. Повтор подготовки из новой формы создаёт новый артефакт.

- `POST /api/cases/{case_id}/revisions/{revision_id}/r3-artifacts`: `idempotency_key` (UUID), `expected_revision_checksum`, `sender_id`, `receiver_id`, `purpose`, `scenario`, `reason`; необязательно `batch_id`, `message_id`, `previous_artifact_id`.
- `GET /api/cases/{case_id}/r3-artifacts/{artifact_id}`: зафиксированные результаты/метаданные, `download_url` только при отсутствии блокирующих ошибок.
- `GET /api/cases/{case_id}/r3-artifacts/{artifact_id}/download`: сохранённые XML-байты, сверка размера/SHA, `no-store`, безопасное имя файла. Отсутствие/порча файла — 409, повторной сериализации нет.
- HTML GET/POST `/cases/{case_id}/r3-export`, GET-параметры `revision_id` / `artifact_id`.

Сервер требует `view` и `export`, для подготовки также `icsr_workflow`. HTML-запись защищена CSRF. Артефакт и ревизия проверяются через указанный доступный случай, подмена Case ID отклоняется. Экспорт не изменяет текущую карточку: её блокировка/версия не обходятся записью в клинические данные. Актуальность выбранного источника проверяется по SHA неизменяемой ревизии. Аудит содержит автора, причину, revision ID и XML SHA, без XML/медицинского дампа.

Файл документа читается по ссылке и checksum именно снимка. Исторические ревизии не изменяются и не помечаются автоматически проверенными.

Осознанные ограничения, выдающие **ошибку**, если соответствующее содержимое заполнено:

- MPID/PhPID/TermID и TBD-контексты без подтверждённых систем. Код без системы, конфликт системы с закреплённым контекстом; отсутствующий LLT/версия не равны «словарь не проверен».
- Неоднозначные `local.*` клинические поля (например, свободная строка идентификатора пациента, беременность, контакты первичного источника, сведения КИ вне подтверждённых C.5); требуется содержательное назначение поддержанному элементу, а не удаление факта ради зелёного статуса.
- Legacy/unverified/invalid/ambiguous/unsupported; старые проекции с отличающимся либо отсутствующим каноническим фактом. `projection_coverage` проверяет Patient/Reaction/CaseProduct/CaseNarrative/CaseLiteratureReference, narrative/комментарий/даты Case. Исторические лекарственные плоские поля, свободные длительности/причинность/дозовые ratio, не имеющие надёжного соответствия, не выбрасываются молча.
- Рассчитанные Naranjo/WHO-UMC не превращаются автоматически в свободную оценку отправителя; нужна отдельно подтверждённая текстовая оценка. Внутренние expectedness/listedness, автор/роль/дата оценки и расчётные ответы остаются внутренним обоснованием в снимке, не произвольными расширениями XML.
- Явное `false` серьёзности не превращается в NI; иной NF для E.i.3.2 блокируется. Для остальных поддержанных NF синтаксис сохраняется, полная поэлементная допустимость отмечена как **не проверенная**.
- Файл без назначения source_document/literature, пропавший/изменённый документ, неподдержанный MIME. Поддержаны PDF, text/plain, JPEG, PNG. Исходные XML/ZIP обозначены как свидетельства импорта и не включаются автоматически.

Внутренний учёт/номера PV1, aliases `CaseIdentifier`, аудит, входящие сообщения/передачи и заявки не копируются как расширения. Для внешних иных ID используется явный `case_identifier` C.1.9 в ревизии. `study_site` и `pv_decision` остаются локальными с предупреждением. Различаются исходное фактологическое значение и служебные сведения; источник/история остаются в ревизии.

## Конверт, follow-up и проверки

ID компании/РЗН не предзаполнены. `sender_id` и `receiver_id` задаются явно, используются для партии и вложенного сообщения. `batch_id` и `message_id` задаются явно либо генерируются как `PV1-B-<UUID4>` и `PV1-M-<UUID4>` — локальный способ уникальности, не присвоенные РЗН ID. Внутренние ссылки XML — UUID5 от SHA ревизии, типа и ID повтора, не от названия.

Время создания конверта и исходящего C.1.2 фиксируется UTC с точностью до микросекунд. Входящее C.1.2 остаётся исходным фактом и не выдаётся за время новой итерации. C.1.1/C.1.8.1 берутся из ревизии; внутренний номер ревизии не становится E2B-версией. AS2 Message-ID не создаётся.

`initial` и `followup` выбираются явно. Для локального follow-up требуется предшествующий локально проверенный артефакт того же случая и другая ревизия: та же идентичность/отправитель, сохранённая C.1.4, не уменьшающаяся C.1.5; новый конверт. Предыдущий артефакт не доказывает подачу. Коррекция/аннулирование, retransmission и изменение идентичности не маскируются под follow-up.

Статусы: «Сформирован — обнаружены ошибки» либо «Локальная проверка пройдена»; XSD отдельно. `locally_valid` означает отсутствие ошибок **реализованного набора**, не юридическую готовность к представлению. В каждом результате остаются `not_performed`: полный лицензированный MedDRA (принадлежность/версия/LLT→PT), полный UCUM/ISO/IDMP, все условные правила IG, совместимость с РЗН. NF-условия показываются дополнительно по заполненному полю. Никаких «Отправлен», «Принят» или «Опубликован» при скачивании.

## Хранение и миграция

Новая `IcsrExportArtifact` / `tblIcsrExportArtifacts`: связи case/revision/предыдущий артефакт, revision SHA/schema, envelope/profile/rule/exporter versions, результаты, XML SHA/размер/путь, автор/время/причина, idempotency UUID и хеш запроса. ORM запрещает UPDATE/DELETE; SQLite имеет append-only triggers. Входящий E2BTransmission не используется как исходящая передача.

Сначала уникальный `.part` записывается и `fsync`, затем `os.replace` в `PV_STORAGE_ROOT/r3/<UUID>.xml` либо `.diagnostic.xml`, затем транзакция БД. Существующий `atomic_write/register_new_file` удаляет только новые файлы операции при откате, включая сбой финального commit. Аварийное завершение процесса между rename и commit может оставить не связанную с БД копию; не создаёт запись «готово» без файла. Скачивание дополнительно проверяет целостность. После commit нет перезаписи старого артефакта. Повтор той же формы возвращает тот же артефакт; тот же ключ с другими параметрами — 409. Новый ключ — новый артефакт, в том числе после обновления версии экспортёра.

Добавочная миграция **20261111_0034**, после **20261111_0033**, создаёт только таблицу/индексы/триггеры артефактов. Прежние миграции не менялись; исторические экспорты не выдумываются. Destructive downgrade намеренно отсутствует.

Команда последующего применения (ниже безопасные отдельные локальные пути; для предназначенной базы пути задаются явно):


**Миграция проверена на временной базе 0033 → 0034, рабочая база не изменялась.** Для использования нового экрана предназначенному экземпляру потребуется применить 0034; этап 0/запуск отдельного сервера здесь не повторялись.
