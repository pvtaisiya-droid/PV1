# Проверка перехода старой установки

Состояние проверки на 12.10.2026: рабочая база не обновлялась. В восстановленном
снимке ревизии `20260819_0024` обнаружены две группы повторяющихся
`tblIncomingRequests.message_number`, всего 11 записей. Обновление до
`20261002_0028` отказало до фиксации изменений; байты базы, все строки, схема
и прежняя ревизия сохранились. Это проверка безопасного отказа, а не успешная
миграция реальных данных. У снимка также остаются 184 исходные ссылки Access
без файлов: см. [описание исходного состояния](access-attachment-baseline.md).

Перед обновлением остановите все процессы записи и подготовьте актуальный
снимок по [инструкции восстановления](backup-restore.md). Сначала восстановите
его в новый каталог и проверьте манифест, целостность, внешние ключи и файловые
ссылки. Эксперименты выполняйте на отдельной копии восстановленной базы,
с отдельным `PV_STORAGE_ROOT`. Сохранённый снимок не изменяйте.

```powershell
$env:DATABASE_URL = 'sqlite:///C:/Codex/PV1/.tmp-upgrade-review/database.sqlite3'
$env:PV_STORAGE_ROOT = 'C:\Codex\PV1\.tmp-upgrade-review\storage'
.\.venv\Scripts\python.exe -m app.manage upgrade-db
.\.venv\Scripts\python.exe -m app.manage check-db
```

Пути в примере должны указывать на заранее подготовленные копии. Для базы
без ревизии сначала выполните `check-legacy`, затем `adopt-legacy` на копии.
Принятие исходной ревизии и обновление выполняются одной транзакцией;
ошибка не должна оставлять новый `alembic_version`. Повторное принятие уже
версированной базы отклоняется. Не заменяйте эти проверки командой `stamp head`.

Для дублей и повреждённых ссылок нужен следующий порядок:

1. Сохранить технический отчёт: таблица, ключ/колонка, ID затронутых записей,
   их связи и текущая ревизия. Рабочее содержимое хранить только в защищённом
   локальном отчёте. Сообщение отказа миграции содержит число групп дублей,
   без значений номеров или текста сообщений.
2. По исходным данным выяснить, являются ли совпадения повторным импортом
   одного сообщения или разными сообщениями с одинаковым внешним номером.
   Решение принимает ответственный за данные. Мягкое удаление не снимает
   глобальный уникальный индекс и не является способом обойти отказ.
3. Если одинаковый номер допустим для разных сообщений, пересмотреть правило
   уникальности, модели, импорт и создать отдельную миграцию с тестами. Если
   исходная запись ошибочна, оформить конкретное исправление с основанием,
   автором и новым событием аудита. Не перенумеровывать и не удалять строки
   автоматически; существующий аудит не редактировать.
4. Для отсутствующего родителя восстановить подтверждённую запись или
   исправить конкретную ошибочную ссылку с новым аудитом. Не создавать
   фиктивных родителей и не выключать FK в рабочих соединениях.
5. Испытать согласованные изменения на новой копии. Проверить успешное
   обновление до head, все ограничения против актуальных моделей,
   `PRAGMA foreign_key_check`, сохранение исходных строк и истории, повторное
   обновление/запуск и валидный E2B-импорт с отдельным хранилищем.
6. Проверить откат восстановлением неизменённого снимка в новый каталог и
   сравнить хеши/ревизию/строки/файлы. Только после этого готовить обновление
   рабочей установки в рамках отдельного согласованного действия.

SQLite-миграции временно отключают FK только на соединении обслуживания,
используют явную транзакцию DDL и проверяют ссылки перед commit. Рабочие
соединения включают `foreign_keys=ON`. Для сравнения схемы используется копия
метаданных: три обратные ссылки `tblE2BImportBatches.created_*` откладываются
при сортировке через `use_alter`; ни один FK не удаляется из сравнения.
Это соответствует [описанию циклической сортировки SQLAlchemy](https://docs.sqlalchemy.org/en/20/core/metadata.html#sqlalchemy.schema.MetaData.sorted_tables).
Тест отдельно проверяет каждый FK, PK, уникальное ограничение и индекс, а
также фактический отказ некорректных ссылок после перестройки циклической
таблицы. Замороженная схема `schema_20260930.py` остаётся неизменной.

При лишних файлах в архиве строгая проверка снимка должна отказать. В сеансе
12.10.2026 исходные файлы манифеста совпали по SHA-256; лишними были два
`source/tests/__pycache__/*.pyc`, появившиеся после коллекции тестов из backups.
Для проверки восстановления в новый временный каталог скопирован только
проверенный состав манифеста и сам манифест. Исходный архив не изменялся.
Исправление коллекции pytest из backups остаётся в шаге 11 плана.

## Подготовка конкретного исправления номеров

Продолжение 12.10.2026: пользователь выбрал сохранение **глобальной**
уникальности и отдельное согласование исправлений 11 записей. Все 11 номеров
сопоставлены с исходной CSV Access; у каждой группы различаются партнёры,
даты и хеши исходного текста. Подтверждения повторного импорта одной записи
нет. Модели и правило уникальности не менялись.

`tools/incoming_number_repair.py prepare` открывает явно указанную базу только
для чтения и предлагает минимальный список замен. В каждой группе предложено
оставить номер у самого раннего сообщения; остальные получают свободные
номера своего года выше существующего максимума. Это технический вариант
для просмотра, а не подтверждение правильности номеров по первичным данным.
Список можно изменить до применения; его нужно отдельно согласовать.

```powershell
.\.venv\Scripts\python.exe -m tools.incoming_number_repair prepare --database C:\Codex\PV1\.tmp-upgrade-review\database.sqlite3 --plan C:\Codex\PV1\.tmp-upgrade-review\reviewed-numbers.json
```

В `proposed-repair.json` текущего сеанса предложены девять замен, два исходных
номера сохраняются. Список из 11 строк для просмотра —
`.tmp-audit-step7-review-20261012/review.csv`. Рабочая база и исходная CSV не
изменялись. Согласование этого списка пока не получено.

После согласования сначала испытайте утверждённый план на новой копии:

```powershell
.\.venv\Scripts\python.exe -m tools.incoming_number_repair apply --database C:\Codex\PV1\.tmp-upgrade-review\database.sqlite3 --plan C:\Codex\PV1\.tmp-upgrade-review\reviewed-numbers.json --actor-login existing-maintenance-login --reason 'Основание согласованного исправления' --offline
```

Команда требует существующего активного автора, непустого основания и
остановки процессов записи. Она не создаёт базу при ошибке пути, не меняет
схему и не перезаписывает согласованный файл при подготовке. План содержит
ревизию и SHA-256 всех полей всех входящих записей: при любом изменении базы,
даже прямым SQL без увеличения версии, нужен новый просмотр плана. Проверяются
исходные номера/версии, принадлежность группам дублей, сохранение одного
исходного номера в каждой группе и отсутствие новых коллизий.

Все замены, увеличение версий и новые события `message_number_repair` с
прежним/новым значением, автором, основанием и общим correlation ID фиксируются
одной транзакцией. Прежняя история не меняется. Ошибка записи аудита откатывает
также уже выполненные замены; повторное применение старого плана отклоняется.
Успешная проба на копии не разрешает автоматическое изменение рабочей базы.

На новой реалистичной копии `candidate-final.sqlite3` девять предложенных
замен испытаны с девятью новыми событиями аудита; проверяется переход до head,
сохранность остальных полей/таблиц/прежней истории, модель и повторный запуск.
Итог и ограничения HTTP-проверки импорта записываются в журнал шага 7.
Старые дополнительные уникальные индексы допустимы при точном совпадении
имени, колонок и уникальности с ограничением модели; дополнительное правило
уникальности на иных колонках проверка отвергает.
